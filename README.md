# 集装箱船配载方案核算服务

基于 Python + FastAPI + SQLAlchemy(SQLite) + PuLP(CBC 整数规划求解器) 实现的集装箱船配载方案核算 HTTP 服务。

录入按**堆栈（stack）与层（tier）**编号的槽位、各槽承重、纵向力臂、相邻槽位关系与全船允许力矩区间，以及箱号、重量、危险类别、卸港先后与不相容危险类别对；服务输出**每箱槽位、总力矩与方案修订号**。方案确认后，还可按岸桥数量与每箱吊装时长/时间窗生成**每箱开工、完工分钟与岸桥编号的装船时间表**，并按该排程逐箱登记**实际开工/完工事件（晚到可按分钟重放，首次登记冻结排程基线用于偏差核算）**，或按每个卸港的允许剩余总力矩闭区间生成**逐港卸箱顺序（各步港序、箱号与卸后剩余力矩）**，码头现场执行时还可**逐箱登记实际卸箱（允许偏离预案下一步：当前港取剩余箱最小卸港序号、须为同栈栈顶、卸后力矩入该港原定区间且新状态仍可卸完；首次登记冻结计划与所用箱重/力臂/港区间，方案被取代后只读、历史进度仍可查）**。岸桥停机时，可凭期望实绩版本、非负截至分钟、各进行中箱正整数预计剩余时长、待开工箱时长与时间窗及基线岸桥停机半开区间，按已确认实绩**只读预测全部未完箱的逐箱预计开工/完工分钟与岸桥及全船最晚完工**（进行中箱保持实际岸桥自截至分钟连续作业；预计作业不与同桥作业或停机重叠、下层完工后上层才开工；优先最晚完工最早、平局按箱号升序 `(开工,岸桥)`；无可行安排附中文原因且不保存，原排程/实绩/冻结基线不变）。装船完结交接时，可凭交接号、截止分钟、期望实绩版本、有效流水号集合与最大完工延误阈值申请**不可变交接凭证**（逐箱按冻结基线核算延误，凭证签发后实绩变化不改内容、仅标示是否仍对应当前实绩）。已完成装船交接的当前方案离港前，可登记**覆盖全部箱且封签号互异的预期封签清单**（冻结后不可改写），现场按箱号、实见封签号、检查分钟与全局唯一扫描号**逐箱登记封签扫描**（不符留痕但不算通过），封签损坏时可凭方案、箱号、当前预期原号、新封签号、换签分钟、原因、全局唯一申请号与期望换签版本（方案级初值 0）**逐箱登记只追加的换签**（原清单与历史扫描不可改，新号不得等于旧号或与他箱当前预期重复，换签分钟不早于该箱上次换签；换签后该箱须有检查分钟不早于换签分钟的新登记匹配扫描方可通过），并凭当前交接凭证、期望扫描版本、截止分钟与唯一申请号申请**离港放行凭证**（仅当方案仍确认、交接凭证仍对应当前实绩、每箱放行有效扫描匹配当前预期且不晚于截止分钟时原子签发；换签、后续扫描、实绩更正或方案取代只使凭证显示失效，不改历史内容）。

## 一、配载约束（全部为硬性约束）

1. **承重**：任一槽位上箱的重量不得超过该槽承重；
2. **堆叠支撑**：某层有箱时，其下层（同堆栈层编号相邻的槽）必须有箱，即不允许悬空；
3. **重量次序**：下层箱不得轻于上层箱（`重量(下层) >= 重量(上层)`）；
4. **卸港先后**：早卸港箱不得压在晚卸港箱下方（`discharge_order` 小者先卸，先卸港在上、后卸港在下）；
5. **危险类别相邻**：不相容危险类别的两个箱不得占据互为相邻的槽位；
6. **总力矩**：全船总力矩 `Σ(箱重量 × 所在槽纵向力臂)` 必须落在允许区间 `[min_moment, max_moment]` 内；
7. 每个箱恰好占用一个槽，每个槽至多一箱，方案必须覆盖清单内**全部箱**。

## 二、优选规则（完整可行方案之间）

1. **最大占用层数最小**（占用到的最高 `tier` 最小）；
2. 最大占用层数相同时，**按箱号排序后取槽位编号序列字典序最小**者。

不存在完整可行方案时返回 `422` 并说明“无解”及原因，**不保存任何方案**。

## 三、修订与确认

- 槽位资料与箱清单分别维护、**各自独立编号**：每次成功录入在本类别取得**唯一且递增**的**资料修订号**——录入事务首个语句即写本类别修订号计数器（SQLite 写语句立即取得写锁），两名调度员并发录入按实际提交先后串行化，**不会有两个成功请求拿到同号**；修订号与整份资料在**同一事务原子落库**（并发失败或校验失败既不留半份资料，也不烧号），并由修订号**唯一索引**兜底；
- 按修订号**查询、核算与确认始终指向同一份资料**；
- **启动前置检查与原子升级**：启动时在单条 `BEGIN IMMEDIATE` 写事务内完成建表、冲突检查与旧库补列回填，并以 `schema_versions` 版本号作为完成标记。若历史库已存在同号多份资料（旧版本并发缺陷遗留），明确报出冲突修订号后**中止并整体回滚**，**不任取其一**；须人工核对清理（每个修订号仅保留一份）后再启动。多进程同时启动同一库时只发生一次有效升级（后到者识别已完成状态直接服务），升级中断后重启恢复到一致结构，部分升级的库不对外提供服务（详见“八、启动”）；
- 方案带**方案修订号**：对已确认方案再次核算得到新修订（`revision_no + 1`），同一方案链以 `root_id` 关联；
- 确认方案时必须提交该方案参与的**槽位资料修订号与箱清单修订号**，服务再与当前最新修订核对：
  - 提交修订与方案修订不一致，或资料已产生更新修订（过期）→ 返回 `409` 拒绝，**原方案保持不变**；
- **确认与资料更新的竞态按实际提交先后结算**：锁外预检后，确认在 `BEGIN IMMEDIATE` **写锁内重新核对**“方案所用修订 == 提交修订 == 当时最新修订”三者一致才生效——
  - 预检到拿锁之间**新资料先提交**（或三者不一致）→ 返回 `409`，**草稿、同链旧已确认方案与槽位占用均不变**；
  - **确认先提交**则成功，之后提交的资料更新**不追溯撤销**该已确认方案（按最新资料走 `amend` → `confirm` 取代）；
- 并发确认通过 SQLite `BEGIN IMMEDIATE` 写锁串行化 + `confirmed_slots(slot_code UNIQUE)` 唯一索引兜底，**不会产生冲突的已确认槽位占用**（一个槽位同一时刻至多属于一个已确认方案）；**同一已确认方案的原样重复确认保持幂等**（含并发同内容确认：后到者在写锁内识别已确认并直接返回原方案，不重复占用槽位）；
- 新修订确认后，同一方案链的旧已确认修订变为 `superseded` 并释放槽位占用。

### 本轮调用示例（资料修订号并发分配）

录入、查询、核算、确认接口的输入输出与错误约定不变；变化在于并发录入的修订号分配与启动检查：

```bash
BASE=http://127.0.0.1:8000/api

# 两名调度员并发录入槽位资料：每个成功请求取得唯一且递增的修订号
for i in 1 2 3 4; do
  curl -s -X POST $BASE/slot-revisions -H 'Content-Type: application/json' -d "{
    \"slots\": [{\"code\":\"S${i}01\",\"stack\":\"S${i}\",\"tier\":1,\"capacity\":100,\"arm\":2.0}],
    \"adjacency\": [], \"incompatible_classes\": [],
    \"min_moment\": -100$i, \"max_moment\": 100000
  }" &
done
wait
# -> 各响应的 slots_revision 为 1..4 各一次（不再出现同号）；
#    修订号与整份资料原子落库，按号查询指向提交时的那一份资料
curl -s $BASE/slot-revisions/3

# 箱清单同理（与槽位资料各自独立编号）
curl -s -X POST $BASE/manifest-revisions -H 'Content-Type: application/json' -d @examples/containers.json

# 按号核算与确认（确认仍只接受当时最新修订：过期 409 且草稿不变）
curl -s -X POST $BASE/plans/compute -H 'Content-Type: application/json' \
  -d '{"slots_revision":4,"manifest_revision":1}'
curl -s -X POST $BASE/plans/<plan_id>/confirm -H 'Content-Type: application/json' \
  -d '{"slots_revision":4,"manifest_revision":1}'
```

历史库存在同号多份资料时，启动升级事务报出冲突修订号后中止并整体回滚（不任取其一、不改写）：

```text
RuntimeError: 启动中止：历史库存在同号多份资料（槽位资料修订号 2、3 各存在多份资料；
箱清单修订号 1 各存在多份资料）。同一修订号对应多份不同资料，无法确定唯一资料，
服务不任取其一；请人工核对并清理重复修订（每个修订号仅保留一份）后再启动。
本次升级未提交，库结构与数据保持升级前状态，可清理后重启。
```

## 四、装船时间表（岸桥调度）

方案**确认后**，按方案 ID 提交岸桥数量与每箱吊装参数，服务输出绑定该**方案修订**的可执行装船时间表。

### 提交字段（`POST /api/plans/{plan_id}/schedules`）

| 字段 | 含义 |
| --- | --- |
| `crane_count` | 岸桥数量，**正整数** |
| `entries[]` | 每箱一条，箱项必须与方案修订**完全一致**（缺失或多余均拒绝） |
| `entries[].no` | 箱号 |
| `entries[].duration` | 该箱吊装时长（分钟），**正整数** |
| `entries[].release_minute` | 最早开工分钟，非负整数 |
| `entries[].deadline_minute` | 最迟完工分钟，非负整数；`release <= deadline`，允许恰在此时刻结束 |

### 排程硬约束

1. 每箱恰好由一台岸桥作业一次；
2. 同一岸桥作业区间 `[开工, 完工)` 不得重叠（允许首尾相接）；
3. 同堆栈**下层箱完工后上层箱才可开工**（按配载方案已占用层自底向上）；
4. 每箱满足自身时间窗：`release_minute <= 开工` 且 `完工 <= deadline_minute`。

### 优选规则

1. **全部箱最晚完工时间（makespan）最早**；
2. makespan 相同的方案间，**按箱号升序使 `(开工分钟, 岸桥编号)` 序列字典序最小**
   （同一箱先比开工、再取最小编号岸桥）。

### 保存与生命周期

- 仅 `confirmed` 方案可生成排程；`draft`/`superseded` 返回 `409`；
- 箱项缺失/多余、时间窗倒置等入参问题返回 `422`；时间窗/岸桥能力无解返回 `422` 且**不保存**；
- **保存前在写锁内再次核对方案仍为已确认**：若求解期间方案被新修订取代，返回 `409` 且不保存；
- 同一方案修订重复提交以新排程**原子替换**旧排程；
- 方案修订被新修订确认取代（`superseded`）后，其排程状态转为 **`historical`**：
  仍可通过 `GET /api/plans/{plan_id}/schedules` 或 `GET /api/schedules?historical=true` 查询，
  但不再列入默认的当前排程；
- **空箱方案**：提交 `entries: []`，返回空排程、`makespan = 0`。

### 响应示例

```json
{
  "plan_id": "f256fc9c...",
  "revision_no": 1,
  "status": "current",
  "crane_count": 2,
  "makespan": 20,
  "entries": [
    {"container_no": "C001", "start_minute": 12, "finish_minute": 20, "crane_no": 1, "stack": "A", "tier": 2},
    {"container_no": "C002", "start_minute": 0,  "finish_minute": 12, "crane_no": 1, "stack": "A", "tier": 1},
    {"container_no": "C003", "start_minute": 6,  "finish_minute": 16, "crane_no": 2, "stack": "B", "tier": 2},
    {"container_no": "C004", "start_minute": 0,  "finish_minute": 6,  "crane_no": 2, "stack": "B", "tier": 1}
  ],
  "created_at": "..."
}
```

curl 示例（请求体亦见 `examples/schedule.json`）：

```bash
# 方案确认后提交（422=箱项不一致/时间窗无解且不保存；409=方案未确认或保存前已被取代）
curl -s -X POST $BASE/plans/<plan_id>/schedules \
  -H 'Content-Type: application/json' -d @examples/schedule.json

# 查询当前排程；加 ?historical=true 可同时查历史排程
curl -s "$BASE/schedules"
curl -s "$BASE/schedules?historical=true"

# 按方案修订查询其绑定排程（历史排程同样可查，status=historical）
curl -s $BASE/plans/<plan_id>/schedules
```

## 五、装船实绩登记（逐箱开工/完工，事件重放）

方案**已确认且已有当前装船排程**后，码头按当前装船排程逐箱登记**实际开工、实际完工**。每次登记提交方案编号（路径参数）、箱号、岸桥编号、**非负实际分钟**与**事件流水号**。

### 提交字段（`POST /api/plans/{plan_id}/actual-events`，请求体亦见 `examples/actual_events.json`）

| 字段 | 含义 |
| --- | --- |
| `events[]` | 本次登记的事件列表，**至少一条**；可一次提交多条，允许重复提交（重试） |
| `events[].seq` | 事件流水号，**正整数**，同一方案内唯一；用于重试幂等与冲突识别 |
| `events[].event_type` | `start`=开工、`finish`=完工 |
| `events[].container_no` | 箱号，**必须在该方案中**（否则 `422` 拒绝） |
| `events[].crane_no` | 岸桥编号，正整数，不得超出冻结排程的岸桥数量 |
| `events[].minute` | 实际发生分钟，**非负整数** |

### 前置条件与拒绝码

- 方案不存在 → `404`；方案为 `draft`（未确认）→ `409`；
- **无当前装船排程 → `409`**（须先生成装船时间表）；
- 箱不在方案中、岸桥越界、分钟为负、事件类型非法、批内流水号重复等入参问题 → `422`；
- 方案修订被新修订取代（`superseded`）后，实绩**只读**：仍可查询，再登记返回 `409`。

### 偏差基线冻结

- **首次登记**在写锁内原子复核方案状态，并把**当时的当前排程整表复制冻结**为偏差基线（逐箱基线开工/完工分钟与岸桥编号，另留 `baseline_frozen_at`）；
- 基线一旦冻结不再改变：此后对同一方案修订重排（排程原子替换）或方案被新修订取代，**均不改写已登记实绩与冻结基线**；
- 并发的首次登记通过 SQLite `BEGIN IMMEDIATE` 写锁 + `plan_id UNIQUE` 头记录串行化，基线只冻结一次。

### 晚到事件与重放规则

事件**允许晚到**，不按到达顺序生效：每次登记把已确认事件与新事件合并，按**实际分钟**重放：

1. 分钟小者先处理；
2. **同一分钟先处理完工（finish）、再处理开工（start）**（允许同桥首尾相接）；
3. 分钟与类型都相同时按到达先后（服务端自增序）。

重放下的硬性校验：

- **开工**：该箱尚无开工记录；该岸桥此刻空闲（同桥作业区间 `[开工, 完工)` 不得重叠，允许首尾相接）；**同堆栈其下各层箱均已完工**；
- **完工**：该箱已开工；岸桥与该箱开工岸桥**一致**；完工分钟**严格晚于**开工分钟。

**任一事件使整条重放链非法，则整次登记拒绝（`422`），已登记记录保持不变**（单批原子，批内不会只落一部分）。

### 重试与冲突

- 同一方案内**流水号相同、内容完全相同**的重复提交视为重试：不新增记录，返回 `200` 与**原结果**；含全新流水号的混合重试只追加新事件（`201`）；
- 流水号相同但内容不同（类型/箱/桥/分钟任一变化）→ **冲突 `409`，记录不变**。

### 查询（`GET /api/plans/{plan_id}/actuals`）

返回实绩**版本**、冻结基线、每箱状态（`pending`/`in_progress`/`finished`）、实际起止分钟与实际岸桥、**相对冻结排程的偏差**（`start_delta_minutes`/`finish_delta_minutes`，正=延后、负=提前；`crane_changed`）、**未完箱列表**（未开工或已开工未完工，按箱号升序）、按分钟重放后的流水号顺序 `replay_order`、全部当前有效事件（含首次登记原值 `orig_minute`/`orig_crane_no` 与是否被更正 `corrected`）以及**更正历史 `corrections`**；方案被取代时 `read_only=true`。首次登记前查询返回 `404`。

### 实绩更正（只改分钟或岸桥）

发现已登记的装船实绩**分钟或岸桥录错**时，可对单条已登记事件发起更正：`POST /api/plans/{plan_id}/actual-events/correction`（请求体亦见 `examples/actual_event_correction.json`）。

#### 提交字段

| 字段 | 含义 |
| --- | --- |
| `seq` | **原事件流水号**（正整数）；原事件不存在返回 `404`（未找到） |
| `expected_version` | **期望实绩版本**（正整数）；与当前版本不一致返回 `409`（版本过期） |
| `request_id` | **更正请求号**（非空字符串，同一方案内唯一），用于重试幂等与冲突识别 |
| `event` | **替代的完整事件内容**（结构同登记接口的单条事件） |
| `event.seq` | 须等于外层 `seq`（**沿用原流水号**，改号返回 `422`） |
| `event.event_type` | 须与原事件一致（**沿用原事件类型**，不一致 `422`） |
| `event.container_no` | 须与原事件一致且仍在方案中（**沿用原箱号**，不一致 `422`） |
| `event.crane_no` / `event.minute` | 替代岸桥（正整数，不超过冻结排程岸桥数量）/替代分钟（非负整数）；**只允许改这两项，且至少改一项**（与原事件完全相同返回 `422`） |

#### 生效与拒绝规则

- 更正后把替代事件并入，**按现有规则重放全部有效事件**（按实际分钟、同分钟完工先于开工）；
- **若整条链非法（撞桥、下层未完工即开工、完工桥与开工不一致、完工不严格晚于开工、岸桥越界等），整次更正拒绝（`422`），实绩、版本与更正历史均不变**；
- 更正成功：实绩 **`version` 加 1**（首次登记为 `1`），更新该事件的现行分钟/岸桥，**留存首次登记原值**（事件上的 `orig_minute`/`orig_crane_no`，`corrected=true`）并追加一条**更正历史**（请求号、流水号、期望版本、更正前后版本、更正前后分钟与岸桥）；
- 方案 `draft`（无实绩）→ `409/404`；方案被取代（`superseded`）后实绩**只读**，更正返回 `409`。

#### 重试与冲突

- **同 `request_id` 且同内容**（期望版本、流水号、替代事件完全一致）的重复提交视为重试：返回 `200` 与**首次更正的结果快照**，**即使版本已被后续更正推进也不重复生效**（快照定格在该次更正后的版本）；
- 同 `request_id` 但**异内容** → **冲突 `409`**，记录不变（再次更正请换新的更正请求号）；
- `expected_version` 与当前版本不符（版本过期）→ **冲突 `409`**，记录不变。

#### 与原登记接口的关系

- 原登记接口 `POST /api/plans/{plan_id}/actual-events` **仍按首次登记内容**（`orig_*`）识别同流水号重试与冲突：用**原始内容**重试仍返回 `200`（不会把已更正值改回）；用更正后的内容走登记接口则因与首次登记内容不同而 **`409` 冲突**。要修正分钟/岸桥，请始终使用更正接口。

### curl 示例

## 五之三、岸桥停机剩余作业预测（只读，不落库）

岸桥停机时，按**已确认方案的装船实绩**与**冻结基线**，在给定的**截至分钟**对全部未完箱预测剩余作业：`POST /api/plans/{plan_id}/remaining-forecast`（请求体亦见 `examples/remaining_forecast.json`）。接口为**纯只读计算**：原排程、实绩与冻结基线均不改变，预测结果不保存（重复调用安全）。

### 提交字段

| 字段 | 含义 |
| --- | --- |
| `expected_actual_version` | **期望实绩版本**（正整数）；与当前版本不一致返回 `409`（版本过期） |
| `cutoff_minute` | **截至分钟**（非负整数）；全部实绩事件均不得晚于该分钟（允许恰在该分钟） |
| `in_progress[]` | **各进行中箱**条目：箱号 + **正整数**预计剩余时长；截至时刻已开工未完工箱必须逐条出现 |
| `pending[]` | **待开工箱**条目：箱号 + 正整数时长、非负最早开工/最迟完工分钟（`release <= deadline`） |
| `crane_downtimes[]` | **停机半开区间**条目：冻结基线岸桥编号 + 非负起止分钟，`start < end`（起点不早于终点即拒绝） |

- **箱项须恰好覆盖全部未完箱**：`in_progress` 与 `pending` 的并集必须与截至分钟按分钟重放得到的未完箱集合**完全一致**；缺箱、多箱、方案外箱、把进行中箱报成待开工箱（或反之）均 `422`；同箱同时出现在两组亦 `422`。
- 箱状态由当前生效实绩（含更正后的现行值）按分钟重放确定：`finished`/`in_progress`/`pending`。

### 预测规则（全部为硬性约束）

1. **已完工箱**以实际完工分钟确定同堆栈先后（其完工均不晚于截至分钟，未完箱开工均不早于截至分钟，故已完工下层对未完上层的先后恒成立）；
2. **进行中箱保持实际岸桥**，并自截至分钟**连续作业**至 `cutoff + remaining`：预计区间固定为 `[cutoff, cutoff+remaining)`，不可改桥、不可中断；该固定区间与本桥停机重叠即无解；
3. **待开工箱**须在自身时间窗内（`release <= 开工`、`完工 <= deadline`）且**开工不早于截至分钟**，可分配到任一冻结基线岸桥（编号 `1..baseline_crane_count`）；
4. **全部预计作业**（进行中 + 待开工）互不与同桥其他预计作业或停机半开区间重叠（同桥区间 `[开工, 完工)`、停机 `[起, 止)`，均允许首尾相接）；
5. 同堆栈**下层完工后上层才能开工**（进行中箱按固定预计完工、待开工箱按预计完工传递）。

### 优选规则

1. **全船预计最晚完工时间最早**（makespan：全部未完箱预计完工的最大值）；
2. makespan 相同的方案间，按**全部未完箱箱号升序**使 `(开工分钟, 岸桥编号)` 序列字典序最小（同一箱先比开工、再取最小编号岸桥；进行中箱的开工/岸桥为固定常量）。

求解采用整数规划（PuLP/CBC，空闲缝隙枚举 + 同桥析取），结果在服务内再以 Python 对时间窗、停机/同桥不重叠、堆栈先后逐箱复核，不盲信求解器容差。

### 前置条件与拒绝码

- 方案不存在 → `404`；**无装船实绩登记 → `404`**（未找到）；
- 方案 `draft`（无实绩头）→ `404`；方案已被新修订取代（`superseded`，实绩只读）→ **`409`**；
- 期望实绩版本与当前不一致 → **`409`**（版本过期，记录不变）；
- 存在晚于截至分钟的实绩事件 → `422`，响应体附 `events_after_cutoff`；
- 箱项未恰好覆盖未完箱/含方案外箱/两组分类不符/同箱跨组、待开工箱时间窗倒置、时长或剩余时长非正、停机起点不早于终点（含相等）、停机岸桥编号越界 → `422`；
- **无可行安排**（在制作业固定区间撞停机、待开工箱在时间窗内无法避开停机/在制作业、堆栈先后导致最迟完工超窗等）→ `422`，中文说明原因，**且不保存**。

### 响应示例

```json
{
  "plan_id": "91bf80eb...",
  "revision_no": 1,
  "actual_version": 1,
  "cutoff_minute": 12,
  "baseline_crane_count": 2,
  "crane_downtimes": [{"crane_no": 2, "start_minute": 12, "end_minute": 20}],
  "entries": [
    {"container_no": "C002", "stack": "A", "tier": 2, "kind": "in_progress",
     "start_minute": 12, "finish_minute": 16, "crane_no": 1},
    {"container_no": "C004", "stack": "B", "tier": 2, "kind": "pending",
     "start_minute": 16, "finish_minute": 22, "crane_no": 1}
  ],
  "latest_finish_minute": 22
}
```

- `kind`：`in_progress`=进行中箱（开工分钟即截至分钟、岸桥为实际岸桥）；`pending`=待开工箱。
- `entries` 按箱号升序；**无未完箱**时 `entries` 为空，`latest_finish_minute` 取已完工箱实际最晚完工（无箱为 0）。

### curl 示例

```bash
# 只读预测（200=给出逐箱预计与最晚完工；404=方案/实绩不存在；
#   409=方案已取代/版本过期；422=实绩晚于截至分钟/箱项不一致/时间窗倒置/
#        停机起点不早于终点/桥号越界/无可行安排附中文原因，均不保存）
curl -s -X POST $BASE/plans/<plan_id>/remaining-forecast \
  -H 'Content-Type: application/json' -d @examples/remaining_forecast.json
```

## 五之一、装船完结交接（不可变凭证）

装船完结交接时，对**已确认方案**按已确认方案申请不可变凭证：`POST /api/plans/{plan_id}/handovers`（请求体亦见 `examples/handover.json`）。

### 提交字段

| 字段 | 含义 |
| --- | --- |
| `handover_no` | **交接号**（非空字符串，**全局唯一**）；同交接号同内容请求重试幂等返回原凭证 |
| `cutoff_minute` | **截止分钟**（非负整数）；每箱须在该时刻前（含）完工 |
| `expected_actual_version` | **期望实绩版本**（正整数）；与当前实绩版本不一致返回 `409` |
| `valid_seqs[]` | **有效流水号集合**（正整数、不得重复）；须与当前已登记有效事件的流水号集合**完全一致**（多交/少交均 `409`） |
| `max_finish_delay_minutes` | **允许的最大完工延误分钟**（非负整数）；逐箱按冻结排程基线核算 |

### 接受条件（任一不满足均不生成凭证）

1. 方案存在且状态仍为 **`confirmed`**（未知方案 `404`；`draft`/`superseded` → `409`），且**已有登记实绩**（无实绩 → `409`）；
2. **只接受已登记实绩**：提交的有效流水号集合与当前登记**完全一致**，且期望实绩版本与当前版本一致；
3. **每箱均在截止前完工**（允许恰在 `cutoff_minute` 时刻完工）且**截止后无任何有效事件**（开工或完工均不可）；未完箱、截止后完工、截止后事件 → `422`，响应体分别给出 `unfinished_containers`、`finished_after_cutoff`、`events_after_cutoff`；
4. **逐箱以冻结排程基线计算完工延误**：`完工延误 = max(0, 实际完工分钟 − 基线完工分钟)`（提前完工不计延误）。任一箱延误超过阈值 → **`422`，返回超限箱与偏差且不生成凭证**：

```json
{
  "detail": "存在 1 箱完工延误超过允许阈值 5 分钟，本次交接被拒绝且不生成凭证",
  "cutoff_minute": 30,
  "allowed_max_delay_minutes": 5,
  "exceeded_containers": [
    {"container_no": "C002", "baseline_finish_minute": 18,
     "actual_finish_minute": 20, "finish_delta_minutes": 2,
     "delay_minutes": 2, "allowed_max_delay_minutes": 1}
  ]
}
```

### 成功时固化内容

签发成功（`201`）一次性固化：**方案修订号、各箱实际开工/完工分钟与实际岸桥、冻结排程基线（基线起止与岸桥）、逐箱偏差（开工/完工偏差、是否换桥）、截止分钟、有效流水号集合、实绩版本与实绩指纹**（规范 SHA-256：版本 + 各事件现行流水号/类型/箱号/岸桥/分钟），返回服务端生成的**凭证号** `handover_id` 与摘要 `summary`（箱数、截止分钟、实绩版本、允许/观测最大延误、指纹算法）。

### 生成前写事务复核（不留旧快照）

- 生成在 SQLite `BEGIN IMMEDIATE` **写事务内**再次复核：**方案仍已确认**、**实绩版本未变**、**有效事件未变（指纹一致）与流水号集合未变**；并发的实绩更正或补登若在提交前生效，本次申请返回 `409` 且不生成凭证，**绝不固化更正/补登前的旧快照**；
- 同交接号同内容的**重试优先返回原凭证**（即使其后实绩版本已被更正推进，也不重新评估、不重复生效，返回 `200`）；同交接号**异内容冲突**（含把交接号复用于另一方案）→ `409`，不生成新凭证；
- 被拒绝的申请（422/409）**不占用交接号**：修正内容后可原号重试。

### 凭证不可变与后续查询

- **后续实绩变化不改凭证**：凭证签发后的实绩更正/补登照常走原登记/更正接口，凭证内容保持签发时快照；查询时以 `matches_current_actuals`（当前实绩指纹是否与凭证指纹一致）、`current_actual_version`、`current_fingerprint` **标示凭证是否仍对应当前实绩**；
- **历史凭证仍可读**：方案被新修订取代（`superseded`）后拒绝新交接（`409`），但其历史凭证仍可查询；
- 查询：`GET /api/plans/{plan_id}/handovers`（列该方案全部凭证）、`GET /api/plans/{plan_id}/handovers/{handover_id}`（方案内查询，不属于该方案 → `404`）、`GET /api/handovers/{handover_id}`（按凭证号全局查询，未知凭证 → `404`）。

### 入参校验

输入缺项、交接号空白、`valid_seqs` 为空/含非正整数/批内重复、截止分钟或阈值为负等 → `422`，**拒绝且不写入**。

### curl 示例

```bash
# 签发（201）；请求体亦见 examples/handover.json
curl -s -X POST $BASE/plans/<plan_id>/handovers \
  -H 'Content-Type: application/json' -d @examples/handover.json

# 同交接号同内容重试 -> 200 返回原凭证；异内容（含跨方案复用）-> 409
# 期望版本过期 / 流水号集合不一致 / 方案未确认或已取代 / 无实绩 -> 409
# 未完箱 / 截止后完工或事件 / 完工延误超阈值（附超限箱与偏差）-> 422，不生成凭证

curl -s $BASE/plans/<plan_id>/handovers          # 该方案凭证列表
curl -s $BASE/plans/<plan_id>/handovers/<hid>    # 方案内查询（404=不属于该方案）
curl -s $BASE/handovers/<hid>                    # 按凭证号查询（含匹配标示）
```

## 五之二、离港前封签核对与放行凭证

已完成装船交接的**当前已确认方案**离港前，按箱核对封签并形成放行凭证：**登记预期封签清单 → 现场逐箱扫描 →（封签损坏时）逐箱换签 → 申请放行**。换签不改原清单与历史扫描，只追加逐箱换签链。

### 第 1 步：登记预期封签清单（`POST /api/plans/{plan_id}/seal-manifest`，请求体亦见 `examples/seal_manifest.json`）

| 字段 | 含义 |
| --- | --- |
| `items[]` | 逐箱预期封签；须**覆盖方案全部箱**（不多不少），且**封签号互异** |
| `items[].container_no` | 箱号（须为方案内箱） |
| `items[].seal_no` | 该箱预期封签号（非空字符串） |

- 方案不存在 → `404`；方案为 `draft`/`superseded` → `409`；缺箱/方案外箱 → `422`（响应体给出缺少箱与方案外箱）；封签号重复、箱号批内重复、空封签号等 → `422`；
- **清单冻结后不能改写**：每方案至多一份清单。同方案**同内容重复登记幂等返回原清单**（`200`，提交顺序不同不算异内容）；**异内容冲突**（`409`），原清单不变；
- 响应给出清单内容指纹 `fingerprint`（SHA-256）、当前**扫描版本** `scan_version`（初始为 0）与**换签版本** `seal_version`（方案级，初始为 0；原清单冻结内容始终不变）。

### 第 2 步：现场封签扫描（`POST /api/plans/{plan_id}/seal-scans`，请求体亦见 `examples/seal_scan.json`）

| 字段 | 含义 |
| --- | --- |
| `scan_no` | **扫描号**（非空字符串，**全局唯一**）；同号同内容重试返回原记录，同号异内容冲突 |
| `container_no` | 箱号（须在预期封签清单中，**未知箱号拒绝登记** `422`） |
| `seal_no` | 实见封签号（非空字符串） |
| `check_minute` | 检查分钟（非负整数） |

- 每成功登记一条**新**扫描，扫描版本 `scan_version` **+1**；响应给出该扫描是否匹配预期（`matched`）、登记后是否为该箱当前有效扫描（`effective`）与登记后扫描版本；
- **封签不符的扫描留痕但不算通过**：`matched=false` 照常入库留痕，不计为该箱通过；
- **同箱以检查分钟较晚者为准，同分钟以登记顺序较晚者为准**：每条扫描的 `effective` 标示其是否为该箱当前有效扫描（状态查询实时计算）；
- 同扫描号**同内容重试返回首次登记快照**（`200`，版本定格在首次登记时，不重复推进）；同扫描号**异内容冲突**（含复用至另一方案）→ `409`；被拒绝的登记（422/409）**不占用扫描号**；
- 尚未登记预期清单 → `409`；方案被新修订取代后扫描**只读**（`409`），历史记录仍可查询；
- 登记时 `expected_seal_no` 取该箱**当前**预期封签号（经换签链后的最新新号）；历史扫描记录的 `expected_seal_no`/`matched` **定格登记时结果，换签不回改**。
- 状态查询：`GET /api/plans/{plan_id}/seal-scans` 返回扫描版本、换签版本、逐箱**放行有效扫描**核对状态（`passed`）与全部留痕记录；每条扫描除历史 `matched`/`effective`（按原排序规则）外，另给出 `eligible`（是否为当前放行有效扫描）与 `current_expected_seal_no`。

### 第 2.5 步：封签损坏逐箱换签（`POST /api/plans/{plan_id}/seal-replacements`，请求体亦见 `examples/seal_replacement.json`）

封签损坏时凭方案、箱号、当前预期原号、新号、换签分钟、原因、全局唯一申请号与期望换签版本登记换签。**原清单与扫描留痕不可改**，仅在逐箱换签链追加一条；该箱当前预期封签号随之变为新号。

| 字段 | 含义 |
| --- | --- |
| `replacement_no` | **换签申请号**（非空字符串，**全局唯一**）；同号同内容重试返回首次快照，异内容冲突 |
| `container_no` | 箱号（须在预期封签清单中，**未知箱拒绝** `422`） |
| `old_seal_no` | 该箱**当前预期**封签号（首次换签为清单原号，再次换签为上次新号；不符 → `422`） |
| `new_seal_no` | 新封签号；**不得等于旧号**，**不得与其他箱当前预期封签号重复**（→ `422`） |
| `replace_minute` | 换签分钟（非负整数）；**不得早于该箱上次换签分钟**（允许相等） |
| `reason` | 换签原因（**非空**字符串，纯空白拒绝 → `422`） |
| `expected_seal_version` | **期望换签版本**（方案级，**初值 0**，每成功换签 +1）；与当前不一致返回 `409` |

- 缺清单（`409`）、方案 `draft`/`superseded`（`409`，取代后只读）、未知箱/原号不符/新号同旧号或与他箱当前预期重复/空原因/负数分钟/换签分钟早于上次（`422`）、期望换签版本过期（`409`）均拒绝；**任何失败回滚、不留记录、不推进版本**；
- 同申请号**同内容重试返回首次登记快照**（`200`，不重复推进）；同申请号**异内容冲突**（含跨方案复用）→ `409`；
- 响应含本次后的方案级 `seal_version`、该箱换签点 `scan_id_at_replace`（换签瞬间该箱已存在扫描的最大 id，无扫描为 0）与链上前驱 `previous_replacement_id`；
- **换签与扫描、放行并发时**在 `BEGIN IMMEDIATE` 写事务内原子核对当前方案状态、换签版本与各箱当前预期；
- 换签链查询：`GET /api/plans/{plan_id}/seal-replacements`（全部换签留痕，只追加，按换签先后给出 `previous_replacement_id` 链）与 `GET /api/plans/{plan_id}/seal-replacements?container_no=<箱号>`（仅该箱留痕，未知箱 `404`）。

**换签后放行门控**：旧扫描保持登记时结果，但换签箱**须有换签后新登记**（扫描 id 晚于换签点 `scan_id_at_replace`）且**检查分钟不早于换签分钟**的扫描，再在这些合格扫描中**按原有效扫描排序规则**（检查分钟较晚、同分钟登记顺序较晚）取胜出者；胜出扫描匹配当前预期封签，该箱才可通过放行。

### 第 3 步：申请离港放行（`POST /api/plans/{plan_id}/seal-releases`，请求体亦见 `examples/seal_release.json`）

| 字段 | 含义 |
| --- | --- |
| `release_no` | **放行申请号**（非空字符串，**全局唯一**）；同号同内容重试返回原凭证 |
| `handover_id` | **当前交接凭证号**；须属于本方案且仍对应当前实绩 |
| `expected_scan_version` | **期望扫描版本**（非负整数）；与当前扫描版本不一致返回 `409` |
| `cutoff_minute` | **放行截止分钟**（非负整数）；每箱最新扫描检查分钟须不晚于该时刻（允许恰在此刻） |

### 签发条件（任一不满足均不生成凭证）

1. 方案存在且状态仍为 **`confirmed`**（未知方案 `404`；`draft`/`superseded` → `409`）；
2. **交接凭证仍对应当前实绩**：凭证不存在 → `404`；不属于本方案 → `422`；签发后实绩已更正/补登（指纹不符）→ `409`；
3. 已登记预期封签清单（无清单 → `409`），且**期望扫描版本与当前一致**（过期 → `409`；换签本身不推进扫描版本，放行仍以扫描版本做乐观核对）；
4. **每箱放行有效扫描均匹配当前预期且不晚于截止分钟**：未换签箱按原排序规则取胜出扫描；**已换签箱仅认可换签后新登记（晚于换签点）且检查分钟不早于换签分钟的扫描**，缺合格新扫、胜出扫描封签不符、检查晚于截止 → `422`，响应体分别给出 `missing_scans`（含仅有旧扫描的换签箱）、`mismatched_containers`（含当前预期/实见封签号与检查分钟）、`scans_after_cutoff`。

全部满足时在 `BEGIN IMMEDIATE` **写事务内原子签发**含逐箱结果的**不可变放行凭证**（`201`），固化：方案修订号、**换签版本 `seal_version`**、所用交接凭证（`handover_id`/`handover_no`）、截止分钟、扫描版本、扫描状态指纹（含换签版本，规范 SHA-256）与实绩指纹、逐箱核对结果（**当前**预期/实见封签号、检查分钟、扫描号）。

### 凭证不可变与失效标示

- **换签、后续扫描、实绩更正或方案取代只使放行凭证显示失效，不改历史内容**：查询时以 `is_current` 与 `invalid_reasons` 标示——`plan_not_confirmed`（方案已被取代）、`seals_replaced`（签发后发生过封签换签）、`scans_changed`（无换签但签发后有新扫描）、`actuals_changed`（签发后实绩已更正/补登）；并随附 `current_scan_version`、`current_seal_version`、`current_scans_fingerprint`、`current_actuals_fingerprint` 当前值；凭证签发快照内的逐箱内容与 `seal_version` 始终保持签发时值；
- 同申请号**同内容重试返回原凭证**（`200`，即使其后已失效也不重新评估）；同申请号**异内容冲突**（含跨方案复用）→ `409`；被拒绝的申请**不占用申请号**；
- 查询：`GET /api/plans/{plan_id}/seal-releases`（列该方案全部凭证）、`GET /api/plans/{plan_id}/seal-releases/{release_id}`（方案内，不属于该方案 → `404`）、`GET /api/seal-releases/{release_id}`（按凭证号全局查询，未知凭证 → `404`）。

### curl 示例


## 六、逐港卸箱顺序

方案**确认后**，按方案 ID 提交**每个卸港序号**的允许剩余总力矩闭区间，服务按该方案所用**箱重与槽位力臂**逐箱重算剩余总力矩，输出绑定该**方案修订**的逐港卸箱顺序。

### 提交字段（`POST /api/plans/{plan_id}/unloading`）

| 字段 | 含义 |
| --- | --- |
| `ports[]` | 每个卸港一条；`discharge_order` 必须与该方案箱清单中的卸港序号**完全一致**（不得缺失、多余或重复），顺序可任意提交（服务内部按港序号升序处理） |
| `ports[].discharge_order` | 卸港序号（正整数，小者先卸） |
| `ports[].min_remaining_moment` | 该港允许剩余总力矩闭区间下限 |
| `ports[].max_remaining_moment` | 该港允许剩余总力矩闭区间上限；下限不得高于上限 |

### 卸箱硬约束

1. **逐港**：按卸港序号从小到大，每个卸箱位置只允许卸下属于该港的箱（每港只卸该港箱）；
2. **堆栈先后**：同堆栈上层箱未卸时不得取下下层箱（按配载方案已占用层自底向上的连续链）；
3. **逐步剩余总力矩**：每卸一箱后，以该方案箱重与槽位力臂重算
   `剩余总力矩 = 初始总力矩 − Σ已卸(箱重 × 纵向力臂)`，结果必须落入**该箱所属卸港**的允许闭区间；全部卸完后剩余力矩恒为 0（故末港区间必须包含 0）。

### 优选规则

在所有港口均可完成的卸箱顺序中，取**全程箱号序列字典序最小**者（港口顺序固定，仅在港内/各可行先后间择优）。求解采用整数规划（PuLP/CBC），分块基数编码与完整字典序最小严格等价；求解结果在服务内再以 Python 对全部硬约束逐步复核，不盲信求解器数值容差。

### 保存与生命周期

- 仅 `confirmed` 方案可规划卸箱顺序；`draft`/`superseded` 返回 `409`；
- 卸港序号不一致、区间倒置、重复港序等入参问题返回 `422`；**无可行顺序或求解无法确定同样返回 `422` 且不保存**（中文说明原因，如末港区间不含 0、堆栈先后与某港区间不相交）；
- **保存前在写锁内再次核对方案仍为已确认**：若求解期间方案被新修订确认取代，返回 `409` 且不保存；
- 同一方案修订重复提交以新顺序**原子替换**旧顺序；
- 方案修订被新修订确认取代（`superseded`）后，其卸箱顺序转为 **`historical`**：
  仍可通过 `GET /api/plans/{plan_id}/unloading` 或 `GET /api/unloading?historical=true` 查询，
  但不再列入默认的当前顺序；
- 卸箱顺序与装船排程相互独立：历史顺序/排程仍可查询，**不影响已有配载与装船排程**；
- **空箱方案**：提交 `ports: []`，返回空顺序、初始/最终力矩均为 0。

## 六之一、逐港卸箱执行（现场逐步登记，可偏离预案）

逐港卸箱顺序确认后，码头现场执行时**允许选择不同于预案下一步的箱**逐箱登记：
`POST /api/plans/{plan_id}/unloading/execute`（请求体亦见 `examples/unloading_execute.json`）。
每次提交**方案号**（路径参数）、**箱号**、**全局唯一操作号**与**期望进度版本**。

### 提交字段

| 字段 | 含义 |
| --- | --- |
| `container_no` | 本次实际卸下的箱号；须属当前港且位于同堆栈最上层（箱号空白/不存在 422） |
| `operation_no` | **全局唯一操作号**（非空字符串）：同号同内容重试返回首次结果，同号异内容（含跨方案复用）冲突 |
| `expected_version` | **期望进度版本**（非负整数）；首次为 0，每次成功登记后 +1；与当前不一致返回 `409` |

### 登记规则（任一不满足均不登记、进度不变）

1. **无当前卸箱计划则拒绝**（`409`）：须先生成第六章的逐港卸箱顺序；方案 `draft`/`superseded` 同样 `409`；
2. **当前港**取剩余箱中最小卸港序号；所选箱须**属于当前港**（否则 `422`）；
3. 所选箱须位于其堆栈**剩余箱的最上层**（同堆栈上层未卸不得取下下层，否则 `422`）；
4. 卸后**剩余总力矩须落入该港原定闭区间**（`剩余总力矩 = 上次剩余 − 箱重 × 力臂`，否则 `422`）；
5. **前瞻可行性**：只有从新状态仍能按**港序、堆栈先后与各港力矩区间**卸完全部剩余箱时才登记；
   所选箱即时合法但走入死局时返回 `422`，响应体随附 `blocked_reason`（求解器给出的中文阻碍原因）、
   `current_port`、`remaining_moment_after`，**说明阻碍且进度不变**。

### 冻结与生命周期

- **首次登记在 `BEGIN IMMEDIATE` 写锁内冻结**当时的当前卸箱计划（全程箱号顺序）及该计划所用
  **箱重、槽位力臂与各港力矩区间**（逐行快照）；此后对同一方案修订**重排原计划不改已卸记录，
  也不改后续核算所用的箱重/力臂/港区间**；
- 方案修订被新修订确认取代（`superseded`）后，执行进度**只读**：再登记返回 `409`，
  但**历史进度仍可查询**（`status=historical`、`read_only=true`）；
- 全部箱卸完后进度完结（`completed=true`、`read_only=true`），不再接受登记；
- 并发现场登记通过写锁 + 期望进度版本**原子核对**串行化：版本过期（已被并发登记推进）返回 `409`，
  过期版本或非法箱项都**不会留下部分进度**（步骤、版本、冻结快照、操作台账在同一事务内提交/回滚）。

### 重试与冲突

- **同操作号同内容**（箱号与期望版本均一致）的重复提交视为重试：不重复生效，返回 `200` 与
  **首次登记的结果快照**（即使其后进度版本已被其他操作推进，或方案已被新修订取代）；
- **同操作号异内容**（换箱号/换期望版本，或把操作号复用于另一方案）→ **冲突 `409`，进度不变**。

### 查询（`GET /api/plans/{plan_id}/unloading/execution`）

返回**已卸步骤**（逐步港序、箱号、箱重/力臂与卸后剩余力矩）、**当前港**、**剩余力矩**、
**进度版本**与按现有**全程箱号字典序规则**求得的**可行剩余推荐顺序 `recommendation`**
（每步含港序、箱号、槽位/堆栈/层、箱重、力臂与卸后剩余力矩；全部卸完为空），另含：

- `planned_next_container`：冻结的**原计划**下一步箱号（现场可改选其他合法箱，两者形成对照）；
- `frozen`/`frozen_at`：计划是否已被首次登记冻结及冻结时刻；
- `status`（`current`/`historical`）、`read_only`、`completed`、`initial_moment`。

首次登记**前**查询（已有卸箱计划）返回 `progress_version=0`、`frozen=false` 的预览，
推荐顺序即原计划；无卸箱顺序或方案不存在返回 `404`。

### curl 示例

```bash
# 首次登记（期望版本 0）；201=登记成功；响应给出从新状态出发的可行剩余推荐顺序
curl -s -X POST $BASE/plans/<plan_id>/unloading/execute \
  -H 'Content-Type: application/json' -d @examples/unloading_execute.json

# 同操作号同内容重试 -> 200 返回首次结果快照；同号异内容（含跨方案）-> 409
# 期望版本过期/并发已推进、方案未确认或已取代只读、卸箱计划缺失、已完结 -> 409
# 箱不属当前港/不在栈顶/已卸过/箱号未知、卸后力矩出区间、新状态无可行后续（附阻碍原因）-> 422
curl -s -X POST $BASE/plans/<plan_id>/unloading/execute \
  -H 'Content-Type: application/json' \
  -d '{"container_no":"C003","operation_no":"UNLOAD-0002","expected_version":1}'

# 查询：已卸步骤、当前港、剩余力矩、进度版本与字典序最小的可行剩余推荐顺序
curl -s $BASE/plans/<plan_id>/unloading/execution
```

## 六之二、收紧剩余力矩安全区间（执行中调整申请）

卸箱执行过程中港口需要收紧剩余力矩安全区间时，可对**已开始且未完结**的已确认方案提交
调整申请：`POST /api/plans/{plan_id}/unloading/window-adjustments`
（请求体亦见 `examples/unloading_window_adjustment.json`）。

### 提交字段

| 字段 | 含义 |
| --- | --- |
| `application_no` | **全局唯一申请号**（非空字符串）：同号同内容重试返回首次结果，同号异内容（含跨方案复用）冲突 `409` |
| `expected_progress_version` | **期望卸箱进度版本**（非负整数）；与当前进度版本不一致（过期或并发登记已推进）返回 `409` |
| `expected_window_version` | **期望区间版本**（非负整数）；首次冻结为 `0`，每次调整生效后 `+1`；与当前区间版本不一致返回 `409` |
| `ports` | **至少一个**当前港至后续未完成港的新区间 `{discharge_order, min_remaining_moment, max_remaining_moment}`；**未列港沿用当前生效区间**；港序号不得重复 |

### 调整规则（任一不满足均拒绝且不生效）

1. 方案必须为已确认、卸箱执行**已开始**（已有首次卸箱登记）且**未完结**：未确认/无计划/已开始校验见“六之一”；
   未开始返回 `409`，方案已被新修订取代（只读）返回 `409`，全部卸完返回 `409`；
2. **不得改已完成港**：每个区间的卸港序号须 ≥ 当前港（剩余箱中最小卸港序号），且属于本方案卸港；
   修改已完成港返回 `422`；
3. 每个新闭区间**上下界须为有限数值**（不得为 `NaN`/`Infinity`/`-Infinity`）且**下界不大于上界**；
4. 新区间必须**包含于该港当前生效区间**（只能收紧，不能放宽或平移出界），否则 `422`；
5. **当前剩余总力矩须落入调整后的当前港区间**（收紧不得否决现状），否则 `422`；
6. **可完成性验证**：依据首次执行冻结的**箱重、槽位力臂与堆栈**，从当前**未卸箱**验证仍能按
   **港序、栈顶规则（同堆栈上层先卸）与逐步新区间**卸完全部剩余箱（MILP，全程箱号字典序规则
   同“六之一”）；**无解返回中文原因且不生效**（`422`，响应体 `detail` 含 `无解原因：...`）。

### 生效与留档

- 全部核对在 `BEGIN IMMEDIATE` 写锁内完成；通过后在**同一事务**内更新生效区间、把
  **区间版本原子 `+1`** 并写入调整留档（任何拒绝均整批回滚，不留部分生效区间）；
- 调整**不推进进度版本、不改已卸步骤**；后续**卸箱登记与剩余推荐顺序一律使用生效区间**核算；
- **原冻结区间**（首次登记时的原定区间）与**原有接口字段全部保留**：执行视图的既有字段
  （`progress_version`、`steps`、`recommendation`、`frozen_at` 等）含义不变；
- 并发调整通过写锁 + 期望进度/区间版本原子核对串行化：版本过期返回 `409`，不生效。

### 查询展示

`GET /api/plans/{plan_id}/unloading/execution` 的响应新增：

- `window_version`：当前**区间版本**（首次冻结为 `0`，每次调整生效后 `+1`）；
- `effective_ports`：各卸港**当前生效**的剩余总力矩闭区间（首次冻结时等于原定区间）；
- `window_adjustments`：**调整历史**列表（按生效先后升序），每条含申请号、申请时期望的
  进度/区间版本、生效后的区间版本、本次列出的新区间与生效时刻。

另提供 `GET /api/plans/{plan_id}/unloading/window-adjustments` 单独查询调整历史
（执行未开始返回 `404`）。

### 重试与冲突

- **同申请号同内容**（期望版本与区间列表完全一致）的重复提交视为重试：不重复生效，返回
  `200` 与**首次生效的结果快照**（即使其后进度/区间版本已推进，或方案已被新修订取代）；
- **同申请号异内容**（换期望版本/换区间，或把申请号复用于另一方案）→ 冲突 `409`，不生效；
- 异内容、期望版本过期、方案已被取代均**不改任何状态**（生效区间、区间版本、调整历史不变）。

### curl 示例

```bash
# 提交收紧申请（期望进度版本 1、期望区间版本 0）；201=首次生效，响应即调整后的执行视图
curl -s -X POST $BASE/plans/<plan_id>/unloading/window-adjustments \
  -H 'Content-Type: application/json' -d @examples/unloading_window_adjustment.json

# 同申请号同内容重试 -> 200 返回首次结果快照；同号异内容（含跨方案）-> 409
# 期望进度/区间版本过期、方案未确认/已取代只读、执行未开始或已完结 -> 409
# 改已完成港、新区间非有限/倒置/未包含于生效区间、当前剩余力矩不在调整后当前港区间、
# 或未卸箱按新区间无法卸完（附“无解原因”）-> 422，均不生效
curl -s -X POST $BASE/plans/<plan_id>/unloading/window-adjustments \
  -H 'Content-Type: application/json' \
  -d '{"application_no":"WINDOW-ADJ-0002","expected_progress_version":1,"expected_window_version":1,
       "ports":[{"discharge_order":2,"min_remaining_moment":-60,"max_remaining_moment":0}]}'

# 查询：生效区间、区间版本与调整历史
curl -s $BASE/plans/<plan_id>/unloading/execution
curl -s $BASE/plans/<plan_id>/unloading/window-adjustments
```

## 七、应急改配（码头临时封锁槽位）

码头临时封锁槽位时，按**当前已确认方案 ID** 与**不可用槽位编号列表**计算应急改配草稿。

### 前置条件（不满足返回 `409`，不保存）

1. 基础方案必须为当前 **`confirmed`** 方案（`draft`/`superseded` 拒绝）；
2. 该方案所用**槽位资料修订**与**箱清单修订**均须为各自的**当前最新修订**
   （资料已更新时，请先按最新资料走 `amend` → `confirm` 再申请应急改配）。

### 提交字段（`POST /api/plans/{plan_id}/restow`，请求体亦见 `examples/restow.json`）

| 字段 | 含义 |
| --- | --- |
| `blocked_slots` | 临时封锁、不可占用的槽位编号列表；**不得为空、不得含重复编号、不得含空白编号**（入参校验失败返回 `422`） |

- 编号须**属于该方案所用槽位资料修订**，未知编号返回 `422`（中文说明，不保存）；
- 封锁列表可包含原本就空着的槽位（此时若无需调整，换槽箱数为 0）。

### 硬性约束（与第一章完全一致，另加封锁约束）

1. **保持原方案全部箱及资料**：以当前最新槽位资料修订与箱清单修订参与计算，箱一个不增不减；
2. **不可用槽位不得占用**（原槽被封的箱必然换槽；其余箱在可行时原位保留）；
3. 继续满足**承重、堆叠支撑、重量次序、卸港先后、危险类别相邻、总力矩**全部既有约束。

### 优选规则（三阶段，整数规划 PuLP/CBC）

1. **最小化相对原方案换槽的箱数**（箱槽与原方案不同即记一次换槽）；
2. 换槽箱数相同时，**最小化最高占用层**；
3. 再相同时，**按箱号升序取槽位编号序列字典序最小**。

求解结果在服务内再以 Python 对全部硬约束逐步复核（含封锁槽占用、原槽被封箱必换），不盲信求解器容差。

### 响应示例

```json
{
  "plan_id": "9c77...",
  "revision_no": 2,
  "status": "draft",
  "root_id": "2f1e529a...",
  "parent_id": "2f1e529a...",
  "slots_revision": 1,
  "manifest_revision": 1,
  "blocked_slots": ["B01"],
  "moved_boxes": 1,
  "max_occupied_tier": 1,
  "total_moment": 60.0,
  "assignments": [
    {"container_no": "C001", "slot_code": "A01", "stack": "A", "tier": 1},
    {"container_no": "C002", "slot_code": "C01", "stack": "C", "tier": 1}
  ],
  "moves": [
    {"container_no": "C002", "from_slot_code": "B01", "to_slot_code": "C01",
     "from_stack": "B", "to_stack": "C", "from_tier": 1, "to_tier": 1}
  ],
  "created_at": "..."
}
```

### 保存与生命周期

- 草稿为方案链上的**新方案修订**（`revision_no = 基础方案修订号 + 1`，同 `root_id`、`parent_id` 指向基础方案），状态 `draft`；
- **草稿不占用任何槽位、不改变原确认方案**：`confirmed_slots` 不动，原确认方案在新草稿确认前**持续有效**；
- **无完整可行改配返回 `422` 且不保存**（中文说明原因，如可用槽不足、承重/堆叠/力矩等约束无法同时满足）；
- **求解后保存前在 `BEGIN IMMEDIATE` 写锁内再次复核**，任一成立即返回 `409` 且不保存：
  - 基础方案已被取代（状态不再是 `confirmed`）；
  - 同方案链（同 `root_id`）出现了更新的方案修订；
  - 基础方案所用槽位资料/箱清单发生变化（出现更新修订）；
- 新草稿确认沿用**现有确认规则**：`POST /api/plans/{draft_id}/confirm` 仍须提交其
  `slots_revision`/`manifest_revision` 并与最新修订核对，仍受槽位唯一占用约束串行化；
  草稿确认后旧确认修订变为 `superseded` 并转移槽位占用，封锁槽位自然不再被占用；
- **空箱方案**：封锁任意槽位均返回空草稿，`moved_boxes = 0`。

curl 示例：

```bash
# 基于当前已确认方案计算应急改配草稿（422=编号非法/无可行改配且不保存；409=未确认/资料过期/保存前已变化）
curl -s -X POST $BASE/plans/<plan_id>/restow \
  -H 'Content-Type: application/json' -d @examples/restow.json

# 草稿确认（沿用现有确认与槽位冲突规则；封锁槽不会被新确认占用）
curl -s -X POST $BASE/plans/<draft_id>/confirm \
  -H 'Content-Type: application/json' \
  -d '{"slots_revision":1,"manifest_revision":1}'
```

### 方式 A：Docker Compose（推荐，一键启动）


镜像构建时完成依赖安装；容器入口 `scripts/entrypoint.sh` 会先幂等初始化数据库表结构，再启动 API。

### 启动前置检查与升级（资料修订号冲突、补列回填、并发/中断安全）

`init_db`（容器入口、本地初始化与 API 启动 lifespan 均会执行）在**对外服务之前**完成建表、冲突检查与旧库补列回填。SQLite 升级在**单条 `BEGIN IMMEDIATE` 写事务**内整体完成，并以 `schema_versions` 中的结构版本号作为“升级已完成”标记：

- **资料修订号冲突中止**：若 `slot_revisions` / `manifest_revisions` 中存在**同号多份**资料，升级事务报出各类别的冲突修订号后**中止并整体回滚**（`RuntimeError`，不任取其一、不自动挑选或改写）；须人工核对清理（每个修订号仅保留一份）后再启动；
- **无冲突旧库一次性升级**：幂等补齐修订号唯一索引、按各类别**当前最大修订号**回填修订号计数器（随后录入从最大号继续递增，历史修订仍可按号查询），并回填既有数据的新增列——实绩版本（历史实绩为第 1 版）、事件原始分钟/岸桥、卸箱执行区间版本（0）与生效区间（按冻结原定区间回填）、封签清单/放行凭证换签版本（0）；
- **并发启动只升级一次**：同一持久化库被两个（或多个）服务进程同时启动时，先到进程取得写锁完成升级；后到进程在锁外等待，进入后读到版本标记即**跳过升级直接服务**，不重复建表/回填、计数器不回退、不烧号。等待写锁超时（默认 60 秒，有限重试 3 次）才以明确原因中止；
- **中断恢复到一致结构**：SQLite 的 DDL 同样事务化——升级任一步失败或进程被杀死，整笔事务回滚，库恢复到升级前结构；版本标记与全部结构变更在**同一事务**提交，因此库上要么看不到标记（未完成），要么看到完整新结构（已完成），**不存在“部分升级”的中间状态对外提供服务**（lifespan 升级失败时应用启动中止，`/health` 不监听）。再次启动重新升级即可；旧版本多事务迁移可能遗留的“列已补、值未回填”半升级库，重启时按数据不变量（未更正事件的原始值等于现行值、每执行已有生效区间、各类别计数器一行）继续补齐，已更正行与既有计数永不被覆盖；
- **失败可定位**：冲突、各升级步骤失败与长期拿不到写锁的错误信息均标明阶段与底层原因；API 进程把异常栈写入日志后再退出，容器可据此排查（`docker compose logs stowage`）。

> HTTP API 的请求体、响应体与状态码均不随升级改变；升级完成后现有接口照常可调用（见下例）。启动方式（Docker Compose / Docker / 本地 uvicorn / 手工 `python -c "from app.database import init_db; init_db()"`）保持不变，无需新增命令或参数。

### 录入字段说明

槽位 `slots[]`：

| 字段 | 含义 |
| --- | --- |
| `code` | 槽位编号（建议定长如 `A01`，字典序即层位次序） |
| `stack` | 堆栈编号；同堆栈按 `tier` 自底向上构成堆叠关系 |
| `tier` | 层编号，自底向上从 1 开始的正整数 |
| `capacity` | 槽位承重，非负 |
| `arm` | 纵向力臂 |

`adjacency`：相邻槽位编号对（无向），如 `[["A01","B01"]]`。
`incompatible_classes`：不相容危险类别对，如 `[["1","5"]]`。

箱 `containers[]`：

| 字段 | 含义 |
| --- | --- |
| `no` | 箱号（同一清单内唯一） |
| `weight` | 重量，必须大于 0（否则“非法重量”报错） |
| `hazmat` | 危险类别字符串；普通箱传 `null` |
| `discharge_order` | 卸港先后正整数，小者先卸 |

### 错误处理

- `400/404`：业务错误（修订/方案/排程/卸箱顺序/**卸箱执行进度**/**装船实绩/交接凭证**不存在等），中文 `detail`；**卸箱执行在方案未知或方案无卸箱顺序（且无执行进度）时返回 404（未找到）**；**实绩更正还在方案不存在、无实绩登记头或原事件流水号未找到时返回 404（未找到）**；**装船完结交接还在方案未知、凭证号未知或凭证不属于路径所给方案时返回 404（未找到）**；**封签核对还在方案未知、未登记预期清单（查询/扫描状态）或放行凭证号未知/不属于路径所给方案时返回 404（未找到）**；**岸桥停机剩余作业预测还在方案未知或方案无装船实绩登记时返回 404（未找到）**；
- `409 Conflict`：资料修订过期/不一致、重复确认、并发槽位占用冲突、对未确认方案排程或规划卸箱顺序、排程/卸箱顺序保存前方案已被新修订取代，原数据不变；**应急改配还在基础方案非已确认、资料非最新、或保存前基础方案被取代/同根出现新修订/资料变化时返回 409，原确认方案仍有效**；**装船实绩还在方案未确认/无当前排程、方案已被新修订取代（实绩只读）、同方案流水号同号异内容时返回 409，记录不变**；**实绩更正还在方案已被取代（只读）、期望实绩版本过期、同更正请求号提交异内容时返回 409，实绩/版本/更正历史不变**；**装船完结交接还在方案未确认或已被取代、无已登记实绩、期望实绩版本过期、有效流水号集合与登记不一致、同交接号异内容（含跨方案复用同一交接号）、或写事务生成前复核发现方案状态/实绩版本/有效事件（指纹）已被并发更正或补登改变时返回 409，不生成凭证**；**逐港卸箱执行还在方案未确认（draft）、无当前卸箱计划、方案已被新修订取代（进度只读）、全部箱已卸完、期望进度版本与当前版本不一致（过期或并发登记已推进）、同操作号提交异内容（含把全局唯一操作号复用于另一方案）时返回 409，进度不变**；**卸箱区间调整还在执行未开始（无首次卸箱登记）、执行已完结、方案已被新修订取代（只读）、期望卸箱进度版本或区间版本与当前版本不一致（过期或并发登记/调整已推进）、同申请号提交异内容（含把全局唯一申请号复用于另一方案）时返回 409，生效区间、区间版本与调整历史均不变**；**封签核对还在方案未确认（draft）或已被取代、预期清单已冻结而异内容重登、扫描号同号异内容（含跨方案复用）、未登记预期清单即扫描时返回 409，清单与扫描记录不变**；**封签换签还在方案未确认或已被取代（只读）、未登记预期清单、期望换签版本过期（含并发换签已推进版本）、同换签申请号异内容（含跨方案复用）时返回 409，换签链与换签版本不变**；**离港放行还在方案未确认或已被取代、交接凭证已不对应当前实绩、未登记预期清单、期望扫描版本过期、同申请号异内容（含跨方案复用）时返回 409，不生成凭证**；**岸桥停机剩余作业预测还在方案修订已被新修订取代（实绩只读）或期望实绩版本与当前版本不一致（版本过期）时返回 409，不保存任何内容**；

## 十二、请求示例（curl）

```bash
BASE=http://127.0.0.1:8000/api

# 1) 录入槽位资料（得到 slots_revision）
curl -s -X POST $BASE/slot-revisions -H 'Content-Type: application/json' -d '{
  "slots": [
    {"code":"A01","stack":"A","tier":1,"capacity":100,"arm":2.0},
    {"code":"A02","stack":"A","tier":2,"capacity":100,"arm":3.0},
    {"code":"B01","stack":"B","tier":1,"capacity":100,"arm":2.0},
    {"code":"B02","stack":"B","tier":2,"capacity":100,"arm":3.0}
  ],
  "adjacency": [["A01","B01"],["A02","B02"]],
  "incompatible_classes": [["1","5"]],
  "min_moment": -100000,
  "max_moment": 100000
}'

# 2) 录入箱清单（得到 manifest_revision）
curl -s -X POST $BASE/manifest-revisions -H 'Content-Type: application/json' -d '{
  "containers": [
    {"no":"C002","weight":20,"hazmat":null,"discharge_order":1},
    {"no":"C001","weight":10,"hazmat":null,"discharge_order":1}
  ]
}'

# 3) 核算方案（可省略修订号，默认取双方最新修订；无解返回 422 且不保存）
curl -s -X POST $BASE/plans/compute -H 'Content-Type: application/json' -d '{}'
# -> assignments: C001->A01, C002->B01；total_moment=60；revision_no=1

# 4) 确认方案（核对资料修订；过期/冲突返回 409，原方案不变）
curl -s -X POST $BASE/plans/<plan_id>/confirm \
  -H 'Content-Type: application/json' \
  -d '{"slots_revision":1,"manifest_revision":1}'

# 5) 资料更新后修订并重新核算（生成 revision_no=2 的草稿，原确认方案暂保持）
curl -s -X POST $BASE/plans/<plan_id>/amend \
  -H 'Content-Type: application/json' -d '{}'

# 6) 方案确认后生成装船时间表（详见第四章；422=箱项不一致/时间窗无解且不保存）

  -H 'Content-Type: application/json' -d @examples/schedule.json

# 6.1) 码头逐箱登记实际开工/完工（详见第五章；首次登记原子冻结当时排程为偏差基线）
#      201=新事件登记；200=同流水号同内容重试；409=无排程/方案已取代只读/同号异内容冲突；
#      422=箱不在方案/按分钟重放非法（撞桥、下层未完工、完工桥不一致、完工不晚于开工）
curl -s -X POST $BASE/plans/<plan_id>/actual-events \
  -H 'Content-Type: application/json' -d @examples/actual_events.json
curl -s $BASE/plans/<plan_id>/actuals     # 版本/每箱状态/实际起止/偏差/更正历史/未完箱/重放顺序

# 6.25) 岸桥停机时按已确认实绩预测剩余作业（详见第五之三章；只读不保存）
#       200=逐箱预计开工/完工与岸桥、全船最晚完工；404=方案/实绩不存在；
#       409=方案已取代/版本过期；422=实绩晚于截至分钟/箱项不覆盖/时间窗倒置/
#           停机起点不早于终点/桥号越界/无可行安排（附中文原因）
curl -s -X POST $BASE/plans/<plan_id>/remaining-forecast \
  -H 'Content-Type: application/json' -d @examples/remaining_forecast.json

# 6.2) 发现分钟或岸桥录错：凭原流水号+期望版本+更正请求号+替代完整事件更正
#      只改 minute/crane_no，沿用原流水号/类型/箱号；成功版本+1（详见第五章）
#      201=更正生效；200=同请求号同内容重试返回首次结果快照；
#      404=原事件未找到；409=版本过期/同请求号异内容/方案已取代只读；
#      422=改了类型或箱号/空更正/更正后重放链非法（实绩、版本、历史均不变）
curl -s -X POST $BASE/plans/<plan_id>/actual-events/correction \
  -H 'Content-Type: application/json' -d @examples/actual_event_correction.json

# 6.3) 装船完结交接：申请不可变凭证（详见第五之一章；请求体亦见 examples/handover.json）
#      201=凭证签发；200=同交接号同内容重试返回原凭证（不重新评估）；
#      404=方案/凭证未找到；409=方案未确认或已取代/无实绩/版本过期/

#      422=入参非法，或未完箱/截止后完工或事件/完工延误超阈值（附超限箱与偏差），不生成凭证
curl -s -X POST $BASE/plans/<plan_id>/handovers \

curl -s -X POST $BASE/plans/<plan_id>/seal-scans \

curl -s $BASE/plans/<plan_id>/seal-scans   # 扫描状态：版本/逐箱通过/全部留痕
#      c) 申请放行：当前交接凭证+期望扫描版本+截止分钟+唯一申请号

curl -s $BASE/plans/<plan_id>/unloading/execution
```
